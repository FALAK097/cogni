# Waitlyze → Cogni competitive analysis

Research date: **10 November 2026**. Recommendation: borrow Waitlyze's complete, understandable workflow and commercial contract; retain Cogni's support-specific product model. The strongest opportunity is dependable knowledge-grounded support with a reviewed improvement loop, rather than another collection of integrations.

## Product strategy, journeys and information architecture

**Waitlyze sells a finished launch job.** Its headline, “Your launch starts before launch day,” leads to templates and a free entry. The useful object is one waitlist: create a named draft/address → edit a template → check readiness → publish/share/embed → receive and verify signups → encourage referrals → send eligible follow-ups → inspect acquisition and conversion. Builder, Signups, Emails, Analytics and Settings remain in that object's context; Emails is permission-dependent. This makes each capability contribute to a recognizable outcome. [W1–W3, W5]

**Cogni sells a continuing support job.** Its integration-head headline is “AI support, grounded in your knowledge”; primary destinations are **Inbox, Agent, Insights**, with workspace connections in Settings. Agent owns **Build, Test, Deploy**. The corresponding journey is source → grounded preview → reviewed publication → authorized-site installation → visitor question → AI answer or human handoff → teammate reply → feedback/gap → saved test and improvement. This is already a coherent IA; Waitlyze is an adjacent execution benchmark, not a direct support competitor. Do not copy campaign tabs, referrals, or a generic growth dashboard. [C1–C3, C5–C6]

**Onboarding should prove progress.** Waitlyze's active create dialog asks for a name/address and opens Builder; readiness offers specific fixes, and publish options centralize blockers, hosted URL, embed, API, domain and SEO. Its private page test stores checklist results without creating subscribers or sending email; it does **not** establish real deliverability. The four-screen `src/components/onboarding/onboarding.jsx` has no references elsewhere in `src`; its existence is not evidence of the active onboarding journey. [W2–W3]

Cogni already has a source/test/publish/install checklist, immutable publication versions and domain controls. However, `widget-customizer.tsx` derives `hasTestRun` from **any history**, then `agent-readiness.ts` says “regression test case(s) verified.” Installation uses **any session total**, then says the widget is verified on authorized domains. Neither predicate binds success to the current draft, suite, publication or domain; Insights separately supplies `hasObservedSession: false`. These are status-evidence mismatches, not evidence of a security bypass. PR #58 introduces a stronger publication check, so align the existing checklist with that contract rather than building another gate. [C1, C3, C5; PR #58 below]

## Visual system, dashboard and widget UX

**Waitlyze's source-defined design is product-led:** neutral surfaces, dark green ink, lime actions, shared `--product-*` semantic tokens, display/body typography, Paper Mono metadata, tabular numerals, and a repeated green/lime analytics palette. The landing page references actual dashboard/builder imagery and a product walkthrough, with templates as tangible outputs. Those assets and their “live” captions are first-party presentation claims; inaccessible remote media prevents independently verifying their contents or provenance. [W1, W6]

**Cogni should preserve one accepted visual direction.** Integration head uses Geist, blue application/chart tokens and configurable customer-widget branding. Its hero includes an illustrative support UI. [PR #54](https://github.com/FALAK097/cogni/pull/54), based on the delivery-plan branch, already proposes neutral surfaces, Inter/Instrument Serif and broader UI polish; this is pending work, not the current integration design. Reconcile and accept that change before commissioning another restyle. Prefer one truthful, labeled support walkthrough showing source evidence and takeover over decorative sample metrics. [C5–C6; PR #54]

**Waitlyze makes metrics explain decisions.** Analytics documents distinct-browser visitors, impression-linked conversion, verification, zero denominators, missing prior baselines, timezone/range boundaries, chart/table alternatives, errors and retry. It connects low verification to sender health and low conversion to page work. Its waitlist-list conversion intentionally differs from detail conversion; it is not a perfect consistency benchmark. [W4]

**Cogni already has meaningful operations UX:** unread/filter views, labels, snooze, saved replies, reply/note distinction, customer/channel context, editable copilot drafts, ticket controls and explicit uncertain-send confirmation. Insights exposes feedback, no-source-match and unanswered gaps, source conversations, verified Q&A and saved test history. Preserve these. The opportunity is explaining metrics and linking them to recovery: closed status is not customer-confirmed resolution; retrieval matches are not correctness; mean AI response time is not human first-response SLA. Add definitions and evidence denominators before a reporting builder. [C2–C3]

**The widgets have different responsibilities.** Waitlyze embeds a sandboxed, titled iframe; loader origin comes from its own script URL, only bounded referral/UTM fields are forwarded, duplicate frame creation is avoided, and resize messages require matching origin **and** frame window. Its visitor contract separates submission, confirmation, marketing consent and referral credit. [W5]

Cogni maintains a streamed conversation, attachments, feedback, history and human ownership. It already has signed visitor bootstrap claims, domain authorization, safe Markdown handling, interrupted-stream recovery, focus styles and reduced-motion rules. Its harder acceptance case is takeover during generation, reconnect/history consistency, attachment access and a reachable phone composer. Complete that support round trip under #20/#40; an iframe conversion or more widget decoration does not establish it. [C2, C4–C5]

## Architecture, reliability and commercial readiness

Both are Next.js/React applications with Better Auth, PostgreSQL and R2. Waitlyze uses mostly JS/JSX, Prisma, Resend/Cloudflare email, Dodo Payments and OpenNext/Worker build scripts. Cogni uses TypeScript, Drizzle, AI SDK/providers, Cloudflare AI Search, Composio and Vercel-hosted Node routes plus a separate ingestion Queue Worker. Neither a framework version nor a successful build proves runtime reliability. [W8 and `package.json`; C4–C6]

Waitlyze's durable product records include publication revisions, rehearsals, point ledger, email outbox, automation versions/steps, webhook deliveries, consent and workspace audit events. Email dispatch rechecks recipient eligibility/suppression, uses provider idempotency and bounded retries; outgoing webhooks have signatures, claim/retry state and delivery logs. The cron dispatcher is a documented operational dependency. New-format API keys are hashed, waitlist/scoped, expiring/revocable, and rechecked against access. These are credible recoverability mechanisms, not an exactly-once or production-uptime guarantee. [W8–W9]

Cogni already has durable ingestion jobs, atomic claims, retries/DLQ, shared Postgres rate limits, guarded actions and cursor-based conversation events. The UI still polls the event endpoint every **3.5 seconds**, alongside other polling; #20's Durable Object/typing/read ambition is not completed merely by durable events. JSON conversation history is an intentional project invariant, not a missing relational Message table to “fix.” Existing docs retain provider, migration and authenticated-browser release gates. [C2, C4, C6; `AGENTS.md`]

**Why Waitlyze feels worth paying for:** the customer can understand the deliverable, reach a usable published artifact, retain/export an audience, connect follow-ups, diagnose delivery, and buy a clearly defined expansion. Public copy offers Free (one waitlist, 100 cumulative workspace signups, one member) and Pro (**$15/month or $50/year**, subject to regional checkout pricing/tax). Server entitlements gate capacity/features; signup usage survives deletion; subscription periods, cancellation, past-due status, signed/deduplicated payment events and checkout reconciliation have implementation. This supports a credible paid contract; revenue, conversion, merchant activation and production payment correctness remain unverified. Do not copy “unlimited” pricing into a token-cost product. [W1, W7–W8]

Cogni has telemetry foundations but `getPlanLimits()` returns infinity for its listed resources and no equivalent billing lifecycle was found in the reviewed integration paths. The repository's $49/$149/Enterprise pricing component is **not mounted by `src/app/page.tsx`**; treat it as unused copy, not a live offer. #38 already owns metering and gates, but its “$5 Workers-plan-friendly” framing predates the current Vercel/Neon architecture. Update its cost assumptions before choosing price, allowances or a payment vendor. [C4–C6]

1. Refresh PR #48 and Phase 0 evidence; resolve current auth/migration/provider blockers and correct readiness semantics. Preserve the existing three-destination IA.
2. Accept mobile/widget behavior and the pending source/evaluation/publication stack in dependency order. Turn weak conversations into reviewed, reproducible improvements; measure recurrence without equating closure to resolution.

Retain [#33–#35](https://github.com/FALAK097/cogni/issues?q=is%3Aissue+is%3Aopen) campaigns/feedback/changelog as later investments; Waitlyze's referral/email growth loop does not justify copying them into Cogni's support launch.

This report changes documentation only. Its value claim is a hypothesis grounded in product mechanisms: **teams may pay for a support loop they can deploy, trust, recover and improve**. Neither repository inspection nor visual polish establishes customer outcomes or demand.
